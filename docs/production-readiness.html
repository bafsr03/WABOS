Dónde estamos hoy

WABOS V1 es un sistema funcional end-to-end. En el piloto real, el Empleado IA de STAND 120 cerró una venta completa (saludo → catálogo → precio → logística de delivery a Cieneguilla → captura de datos → handoff a humano).

Arquitectura y límites actuales

Cliente ─▶ WhatsApp ─▶ Motor (Node, siempre encendido)         Dashboard (Next.js 15)
                       ├─ Baileys 6.7.23 (WebSocket)   ◀─REST+WS─┤  Inbox · CRM · Catálogo
                       ├─ Fastify (REST/WS)                       │  Campañas · Cobros · Ajustes
                       ├─ SQLite (better-sqlite3, WAL)            └  Conexión (QR)
                       ├─ Empleado IA + workers (jobs)
                       └─ @anthropic-ai/sdk (Claude)
  • Mono-cliente: un motor = un negocio. Sin business_id, sin login de usuarios — un solo DASHBOARD_TOKEN compartido protege todo el dashboard.
  • El motor NO puede ser serverless: mantiene el socket de WhatsApp abierto → necesita un proceso siempre encendido.
  • Corre con tsx src/index.ts (sin artefacto compilado). Sin Dockerfile, sin CI, sin backups. Node ≥20.
  • CORS: origin:true (abierto), sin rate limiting, secretos (API key, IMAP, webhook) en texto plano en .env/SQLite.
  • WhatsApp vía Baileys (no oficial) — riesgo de baneo del número (ver §Riesgo de baneo).

Hosting — comparación y recomendación

Restricción clave: el motor debe estar siempre encendido (socket de WhatsApp), así que nunca va en serverless/Vercel Functions. El dashboard (Next.js) sí puede ir en cualquier lado.

OpciónMotorDashboardPros / ContrasCosto aprox.
VPS auto-gestionado Recomendado VPS Linux (Hetzner / DigitalOcean / Contabo), systemd o pm2 Mismo VPS detrás de Caddy + Más barato, control total, todo en un lugar.
− Tú administras el servidor.		 ~US$5–12/mes
VPS motor + Vercel dashboard VPS (siempre encendido) Vercel + Dashboard con deploys fáciles + CDN.
− Dos lugares que administrar; CORS/orígenes.		 VPS + Vercel (free/Pro)
PaaS de contenedores Railway / Render / Fly.io (proceso persistente) Igual o Vercel + Menos admin de servidor.
− Más caro al escalar; verifica que el volumen/disco persista (auth + SQLite).		 ~US$10–25/mes
Recomendación para el piloto: un VPS chico (2 vCPU / 2–4 GB). Motor bajo systemd con auto-restart; Caddy como reverse-proxy + TLS automático (necesario para el webhook público y para servir el dashboard con HTTPS). Disco persistente para apps/engine/auth/ (sesión de WhatsApp) y apps/engine/data/ (SQLite + comprobantes). Cuando pases a multi-cliente, este mismo patrón escala a un "connection manager" por número.

Etapa 0 — Go-live del piloto (mono-cliente)

Objetivo: STAND 120 usándolo con clientes reales, de forma estable, sin que se caiga ni se pierdan datos.

0.1 Despliegue en servidor siempre encendido ⬜ P0
  1. Aprovisiona el VPS (§Hosting). Instala Node ≥20, pnpm, git.
  2. Clona el repo privado, pnpm install, copia .env.example → .env con las llaves reales.
  3. Corre el motor como servicio systemd (o pm2 start) con auto-restart y arranque al bootear.
  4. Escanea el QR una vez desde el teléfono del negocio; la sesión queda en apps/engine/auth/.
Listo cuando: el motor se reinicia solo tras un crash/reboot y reconecta a WhatsApp sin intervención.
0.2 Dominio + TLS + webhook público ⬜ P0
  1. Apunta un dominio/subdominio al VPS.
  2. Configura Caddy (TLS automático) como reverse-proxy: dashboard y /api, /ws, /api/webhooks/* del motor.
  3. Verifica que https://tu-dominio/api/webhooks/payment sea accesible (lo necesita el forwarder de pagos).
Listo cuando: el dashboard carga por HTTPS y el webhook responde desde internet.
0.3 Build de producción ⬜ P1
  1. Hoy el motor corre con tsx (interpreta TS en caliente). Para producción: o bien fija tsx como runtime estable, o compila a JS (tsc con outDir) y corre node dist/index.js.
  2. pnpm --filter @wabos/dashboard build + next start (o Vercel) para el dashboard en modo producción (no dev).
Listo cuando: ni motor ni dashboard corren en modo dev.
0.4 Backups de la base de datos + prueba de restore ⬜ P0
  1. La SQLite (apps/engine/data/wabos.db) tiene TODO: clientes, conversaciones, cobros, comprobantes. Hoy no hay respaldo.
  2. Cron diario: sqlite3 wabos.db ".backup respaldo.db" (consistente con WAL) + copia fuera del servidor (S3/Backblaze/rsync).
  3. Respalda también apps/engine/auth/ (sesión de WhatsApp) y data/media/ (imágenes de comprobantes).
  4. Haz un restore de prueba en otra carpeta y confirma que el motor arranca con él.
Listo cuando: existe un backup automático offsite y verificaste un restore real.
0.5 Health check + monitoreo de uptime ⬜ P1
  1. Agrega un endpoint GET /health en Fastify que reporte estado del proceso y de WhatsApp (getWaState()).
  2. Conecta un monitor externo (UptimeRobot/BetterStack) que avise si el motor cae o WhatsApp se desconecta.
Listo cuando: recibes una alerta (correo/WhatsApp) si el servicio se cae.
0.6 Logs persistentes + warm-up del número ⬜ P1
  1. Redirige los logs del motor a archivo con rotación (systemd journal o pm2 logrotate).
  2. Warm-up del número nuevo: úsalo como WhatsApp normal unos días antes de automatizar; no envíes masivos de golpe (ver §Riesgo de baneo).
Listo cuando: puedes revisar logs históricos y el número tiene actividad orgánica previa.

Etapa 1 — Completar pagos

La verificación funciona, pero apenas se conecta a la conversación. Estos son los huecos reales.

1.1 La IA crea el cobro y pide el comprobante ⬜ P0

Hoy los cobros se crean a mano en el dashboard, así que la verificación casi nunca se dispara sola. Es la pieza que conecta todo.

  1. Agrega herramientas de IA en ai/tools.ts: get_pending_charges (responde "¿cuánto te debo?" con la identidad Yape/Plin) y create_charge (montо + concepto), tras cerrar una venta.
  2. Regla en el system-prompt (ai/employee.ts): "al acordar una venta, usa create_charge y pide el comprobante por aquí."
  3. Gátalo con un ajuste (ai_can_create_charge) por si el dueño prefiere crearlos manual.
Listo cuando: el bot, al cerrar una venta, crea el cobro y pide la captura — y el flujo de verificación se dispara solo.
1.2 Validar los parsers de correo con emails Yape/Plin reales 🟡 P0

Los parsers (modules/notification-parse.ts) se probaron con correos sintéticos. Los reales tienen su propio HTML/redacción.

  1. Junta correos reales de aviso de Yape (BCP) y Plin (Interbank/BBVA/Scotiabank).
  2. Ajusta las regex de monto / N° de operación / remitente contra esos formatos.
  3. Recuerda el umbral: el aviso por yapeo solo llega desde S/10; ventas menores no generan correo → caen a revisión (limitación de Yape, no un bug).
Listo cuando: un correo real de Yape/Plin aparece en el panel 🔔 Notificaciones y cruza un comprobante real.
1.3 Forwarder de notificaciones para el webhook ⬜ P1
  1. El webhook funciona pero nada le envía todavía. Opciones: documentar una receta MacroDroid/Tasker (POST del texto del aviso), o integrar un servicio (BiPe Alerta / Yapay) que ya reenvía.
  2. Es el respaldo para pagos < S/10 que el correo no cubre.
Listo cuando: un aviso real del teléfono llega al ledger sin intervención manual.
1.4 Recordatorios / cobros vencidos ⬜ P2
  1. Job auto-reprogramado charge.remind: barre cobros pendientes vencidos, 1 recordatorio/contacto/24h, respeta modo Humano, marca expired tras N días.
  2. Filtro "Vencidos" en la página de Cobros.
Listo cuando: un cobro impago recibe un recordatorio automático y se marca vencido.
1.5 Reportería financiera + registro manual de pago ⬜ P2
  1. Totales en Cobros: cobrado hoy/semana, pendientes, exportar CSV.
  2. Botón "Registrar pago manual" (el schema ya soporta source='manual') para pagos confirmados por teléfono.
  3. Job media.cleanup: retención de imágenes de comprobantes (borrar las viejas no verificadas).
Listo cuando: el dueño ve cuánto entró y puede registrar un pago a mano.
1.6 Guardrails de precisión de la IA ⬜ P1
  1. En el piloto el bot inventó un descuento ("antes S/35" — el precio S/30 sí era real) e improvisó logística (Indrive/Olva/Shalom).
  2. Reglas de system-prompt: nunca inventar descuentos/anclas de precio; política de delivery/pago configurable por el dueño (FAQs/ajustes) en vez de improvisada.
Listo cuando: el bot solo menciona precios/promos/logística que existen en la configuración.

Etapa 2 — Fiabilidad & observabilidad

2.1 Rastreo de errores (Sentry) ⬜ P1
  1. Integra Sentry (o similar) en motor y dashboard para capturar excepciones con stacktrace y contexto.
  2. Hoy los errores solo van a los logs de Pino; un fallo de IA/envío puede pasar desapercibido.
Listo cuando: un error en producción te llega con detalle sin revisar logs a mano.
2.2 Visibilidad de la cola de trabajos 🟡 P2
  1. La tabla jobs ya reintenta y marca dead; falta una vista en el dashboard de jobs dead/atascados.
  2. Un job dead ya fuerza el comprobante a revisión (no se pierde), pero conviene verlo.
Listo cuando: puedes ver y reintentar trabajos fallidos desde el dashboard.
2.3 Apagado limpio + checkpoint de WAL ⬜ P2
  1. Maneja SIGTERM: cierra el socket de WhatsApp y la DB ordenadamente al desplegar.
  2. PRAGMA wal_checkpoint periódico para que el archivo WAL no crezca sin control.
Listo cuando: desplegar una versión nueva no corrompe ni pierde mensajes en vuelo.

Etapa 3 — Seguridad & datos

Manejas datos personales de clientes (chats, teléfonos) y datos de pago. Estos puntos son obligatorios antes de operar con terceros, y muy recomendables incluso para el piloto.
3.1 Autenticación real (reemplazar el token único) ⬜ P0
  1. Hoy un solo DASHBOARD_TOKEN compartido abre todo el dashboard. Cámbialo por login por usuario (aunque sea mono-cliente).
  2. Para multi-cliente, esto se cubre con Clerk en la Etapa 4; para el piloto basta un login simple con sesión.
Listo cuando: el acceso requiere usuario/contraseña, no un token pegado en la URL/localStorage.
3.2 CORS, rate limiting y validación ⬜ P1
  1. Cierra CORS (hoy origin:true) al dominio del dashboard.
  2. Rate limiting en /api y sobre todo en /api/webhooks/payment (endpoint público).
  3. El webhook ya valida x-wabos-secret; revisa que Zod cubra todos los bodies.
Listo cuando: orígenes no autorizados son rechazados y el webhook resiste abuso.
3.3 Secretos cifrados en reposo ⬜ P1
  1. La contraseña IMAP y el secreto del webhook viven en texto plano en la tabla settings (SQLite).
  2. Cífralos en reposo o muévelos a variables de entorno; restringe permisos del archivo de la DB.
Listo cuando: un volcado de la DB no expone credenciales de correo/webhook.

Etapa 4 — Multi-cliente (fundamentos SaaS)

Para vender WABOS a varios comercios. Cambio grande — alinea con el Roadmap v2 (Prioridad #1).

4.1 business_id en todo + Postgres + migraciones ⬜ P1
  1. Agrega business_id a cada tabla y a cada query (aislamiento por comercio).
  2. Migra SQLite → Postgres (Neon) y adopta una herramienta de migraciones (Drizzle o Prisma) — hoy el schema se crea a mano en db/index.ts.
Listo cuando: dos comercios coexisten sin ver datos del otro, con migraciones versionadas.
4.2 Auth / organizaciones / roles (Clerk) ⬜ P1
  1. Clerk para usuarios, organizaciones (un comercio = una org) y roles (dueño/vendedor).
  2. Gating por plan (Básico/Avanzado/Pro/Empresarial).
Listo cuando: cada comercio se registra, invita a su equipo y solo ve lo suyo.
4.3 Connection manager de WhatsApp por comercio ⬜ P1
  1. Hoy un motor = un número. Para multi-cliente: gestor de conexiones (varios sockets Baileys) o un worker/proceso por comercio.
  2. Aísla el estado de sesión y la cola de envío por comercio; decide shared-process vs worker-per-tenant según carga.
Listo cuando: N comercios conectan su propio número desde un mismo despliegue.

Etapa 5 — Cobros del operador & onboarding

5.1 Facturación por suscripción ⬜ P1
  1. Cobro recurrente al comercio: Culqi / Izipay (Perú), Stripe para internacional; Yape/Plin para planes chicos.
  2. Ciclo de vida de suscripción: alta, upgrade/downgrade, impago → suspensión.
Listo cuando: un comercio paga su plan y el acceso se activa/suspende automático.
5.2 Onboarding self-service + topes de costo IA ⬜ P1
  1. Asistente: escanear número → perfil del negocio → catálogo/FAQs, sin intervención tuya.
  2. Medición de uso + tope de costo IA por plan (regla ≤30% del precio del plan) con degradación a modo humano al superarlo.
  3. Consola de operador (tú) para ver comercios, uso y estado de conexión.
Listo cuando: un comercio se da de alta solo y su costo IA nunca supera el margen objetivo.

Etapa 6 — Escala & API oficial

6.1 Adaptador de WhatsApp Cloud API (oficial) ⬜ P2
  1. Baileys (no oficial) tiene riesgo de baneo. Ofrece la API oficial de WhatsApp (Cloud API) como plan premium.
  2. Aísla Baileys detrás de la capa wa/ para que el adaptador oficial entre sin tocar el resto.
Listo cuando: un comercio puede correr sobre la API oficial sin baneo.
6.2 Cola distribuida + almacenamiento de media + escala horizontal ⬜ P2
  1. La cola jobs (SQLite) fue diseñada como escalón hacia BullMQ/Redis: reemplaza solo jobs/queue.ts.
  2. Comprobantes/media a object storage (S3/R2) + CDN en vez del disco local.
  3. Escala horizontal del dashboard/API; el motor sigue con afinidad por número.
Listo cuando: el sistema soporta cientos de comercios sin cuellos de botella.

CI/CD

Hoy: sin .github, sin pipeline. Recomendado:

  • GitHub Actions en cada PR: pnpm typecheck + pnpm --filter @wabos/engine test (los 32 tests) + build del dashboard.
  • Deploy en merge a main: pull en el VPS + reinicio del servicio (o deploy del dashboard a Vercel).
  • Protege main (checks obligatorios antes de merge).

Riesgo de baneo de WhatsApp

El mayor riesgo operativo del piloto. Baileys es no oficial; un baneo del número = el negocio se queda sin bot. Ya hay mitigaciones (jitter de envío 2–5s, throttle de campañas 6–12s). Además:
  • Warm-up: usa el número como WhatsApp normal días antes de automatizar.
  • Nunca envíos masivos a números que no te escribieron primero; respeta el throttle de campañas.
  • Usa un número secundario/dedicado, no el personal del dueño.
  • Ten un plan B: si el número cae, re-escanear con otro; a mediano plazo, la API oficial (Etapa 6).

Legal & datos (Perú)

  • Protección de datos personales (Ley N° 29733): manejas teléfonos, nombres y chats. Define retención, finalidad y un aviso de privacidad; permite borrado a pedido.
  • Datos de pago: guardas imágenes de comprobantes y N° de operación. Trátalos como sensibles (acceso restringido, retención acotada — job media.cleanup).
  • Términos de WhatsApp: la automatización vía API no oficial va contra los ToS de WhatsApp; comunícalo como riesgo y migra a la API oficial para clientes que lo requieran.
  • Transparencia con el cliente final: el mensaje ya evita afirmar "dinero recibido" (dice "verificado por comprobante/banco"); mantén ese lenguaje honesto.
