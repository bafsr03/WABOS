Qué estás armando

Dos nombres públicos, un solo Caddy, apuntando a la máquina que esté corriendo el stack en cada momento:

wabos.co        → Caddy → web:3001        (landing — apps/web)
app.wabos.co    → Caddy → dashboard:3000  (el dashboard)
                        → engine:4000     (/api/* y /ws, vía Caddy)

🖥️ Hoy — Camino A

Caddy corre en Docker en la Mac del dueño; un túnel de Cloudflare lo expone a internet con HTTPS real — sin VPS, sin abrir puertos, sin IP pública.

☁️ Después — Camino B

El mismo stack de Docker Compose, movido a un VPS; Caddy emite su propio HTTPS con Let's Encrypt directamente. Cambiar es DNS + dos líneas del .env, no una reconstrucción.

Paso 0 (una vez, habilita los dos caminos) — DNS de wabos.co en Cloudflare

El túnel de Cloudflare necesita administrar el DNS de wabos.co, y no puede hacerlo mientras el dominio use los nameservers por defecto de GoDaddy — un CNAME hacia un túnel no se puede poner en GoDaddy en el dominio raíz (wabos.co mismo, no solo app.wabos.co); es una limitación general de DNS, no una rareza de GoDaddy. La solución es gratis y no cambia tu registrador:

  1. Panel de Cloudflare → Add a site → escribe wabos.co → elige el plan Free.
  2. Cloudflare escanea tu DNS actual de GoDaddy y muestra una pantalla "Review your DNS records". Es probable que incluya uno o dos registros A para @ apuntando a una IP de GoDaddy (su página de dominio aparcado por defecto) — eso no es nada que WABOS use. Borra esos registros A en esa misma pantalla (deja TXT _dmarc, CNAME www y CNAME _domainconnect tal cual — son inofensivos, no tienen que ver con este montaje), y luego Continue to activation.
    No pierdas tiempo agregando o editando registros A directamente en el editor de DNS de GoDaddy antes de esto — en cuanto cambies los nameservers en el siguiente paso, el editor de GoDaddy deja de ser lo que internet realmente lee, así que cualquier registro agregado ahí ahora es esfuerzo perdido. Limpia dentro de la pantalla de revisión de Cloudflare.
  3. Cloudflare te muestra dos nameservers (p.ej. xxx.ns.cloudflare.com, yyy.ns.cloudflare.com). En GoDaddy → My Products → wabos.co → DNS → Nameservers → Change → Enter my own nameservers → pega los dos de Cloudflare (reemplazando el par nsXX.domaincontrol.com por defecto de GoDaddy). GoDaddy sigue siendo tu registrador (donde renuevas/pagas); Cloudflare pasa a ser donde viven los registros DNS.
  4. Espera a que Cloudflare muestre la zona como Active (normalmente bastante menos de una hora, a veces minutos). Revisa cuando quieras con: 
    dig +short NS wabos.co
    Cuando muestre los nameservers de Cloudflare, ya puedes seguir — no avances al Paso A2 antes de esto, o los comandos de DNS del túnel van a fallar.
Este cambio único es también lo que hace que pasar a un VPS más adelante sea trivial: solo vas a editar registros dentro de la misma zona de Cloudflare (CNAME → A), sin tocar nameservers otra vez.

Camino A — Ahora mismo: Mac + túnel de Cloudflare

A1 · Asegúrate de tener cloudflared instalado y logueado

brew install cloudflared
cloudflared tunnel login       # abre el navegador, elige la zona wabos.co

A2 · Crea (o reutiliza) un túnel con nombre

Si todavía no tienes uno para WABOS:

cloudflared tunnel create wabos

Esto imprime un tunnel ID y guarda las credenciales en ~/.cloudflared/<tunnel-id>.json. Si ya tienes un túnel wabos de un montaje anterior, reutilízalo — no hace falta crear un segundo.

A3 · Apunta los dos hosts al túnel

cloudflared tunnel route dns wabos wabos.co
cloudflared tunnel route dns wabos app.wabos.co

Cada comando agrega un registro CNAME en Cloudflare apuntando ese host a <tunnel-id>.cfargotunnel.com. Cloudflare termina el HTTPS para los dos — Caddy en la Mac solo ve HTTP plano.

A4 · Configura el túnel para reenviar los dos hosts a Caddy

Edita (o crea) ~/.cloudflared/wabos-config.yml:

tunnel: wabos
credentials-file: /Users/<tu-usuario>/.cloudflared/<tunnel-id>.json

ingress:
  - hostname: wabos.co
    service: http://localhost:80
  - hostname: app.wabos.co
    service: http://localhost:80
  - service: http_status:404

Los dos hosts reenvían al mismo puerto local 80 — Caddy los distingue por el header Host (que cloudflared preserva) y enruta internamente al contenedor correcto, igual que haría en un VPS.

Instálalo como servicio en segundo plano para que sobreviva reinicios:

sudo cloudflared service install --config ~/.cloudflared/wabos-config.yml
Si ya tienes un agente launchd com.wabos.cloudflared de un montaje anterior, edita su config en el mismo lugar en vez de instalar un segundo servicio.

A5 · El .env — la única diferencia con el camino VPS

cp .env.example .env
nano .env
APP_DOMAIN=http://app.wabos.co
MARKETING_DOMAIN=http://wabos.co
ALLOWED_ORIGIN=https://app.wabos.co
DASHBOARD_URL=https://app.wabos.co
NEXT_PUBLIC_APP_URL=https://app.wabos.co
⚠️ El prefijo http:// en APP_DOMAIN/MARKETING_DOMAIN es todo el truco. Le dice a Caddy "sirve exactamente este host por HTTP plano, sin certificado" en vez de su comportamiento por defecto de "consígueme un certificado real de Let's Encrypt para este host" — que fallaría acá, porque el TLS público lo maneja Cloudflare, no Caddy. Todo lo demás (las URLs https:// que ven tus usuarios, NEXT_PUBLIC_APP_URL para los botones de la landing) queda exactamente igual que en el montaje con VPS, porque esa sí es la dirección externa real.

Llena el resto de los secretos (POSTGRES_PASSWORD, JWT_SECRET, etc.) según la §4 de la guía de despliegue — es idéntico en los dos caminos.

A6 · Lanzar

docker compose up -d --build
docker compose logs -f engine     # espera "WABOS engine is running"

Activa que Docker Desktop arranque al iniciar sesión (Settings → General) para que el stack vuelva solo después de un reinicio — mismo límite de siempre: la Mac tiene que quedarse despierta y con internet, o WABOS deja de responder y WhatsApp puede desvincularse. Está bien como puente; no es 24/7 de verdad.

A7 · Verifica

  • https://wabos.co carga la landing (se ve el candado — es el certificado de Cloudflare, no el de Caddy).
  • "Empezar gratis" apunta a https://app.wabos.co/login.
  • https://app.wabos.co carga el login del dashboard.
  • docker compose exec engine pnpm --filter @wabos/engine create-user, y luego entra en https://app.wabos.co.

Continúa con la guía de despliegue desde §8 en adelante para vincular WhatsApp, la prueba de humo, R2 y backups.

Camino B — Más adelante: pasar al VPS

Cuando quieras salir de la Mac, el trabajo de DNS del Paso 0 se reutiliza — solo cambias registros, no nameservers otra vez.

  1. Levanta el VPS: Hetzner Cloud → CX23 (2 vCPU/4 GB), Ubuntu 24.04, región cercana a tus usuarios. Agrega tu llave SSH, anota la IPv4 pública.
  2. Cambia el DNS en el panel de Cloudflare (la misma zona del Paso 0) — borra los dos registros CNAME del túnel, agrega dos registros A en su lugar:
    TipoNombreValorEstado de proxy
    A@<IP del VPS>DNS only (nube gris)
    Aapp<IP del VPS>DNS only (nube gris)
    Pon el estado de proxy en DNS only, no proxied — Caddy necesita completar su propio desafío de Let's Encrypt y dejar pasar /ws sin tocar, y el proxy de Cloudflare interferiría con eso.
  3. Instala Docker en el VPS — sigue la §2 de la guía de despliegue.
  4. Sube el código al servidor y en el .env: 
    APP_DOMAIN=app.wabos.co
MARKETING_DOMAIN=wabos.co
    (quita los prefijos http:// — todo lo demás del .env queda igual, incluido NEXT_PUBLIC_APP_URL, así que no hace falta reconstruir las imágenes, solo el nuevo .env en la máquina nueva.)
  5. docker compose up -d --build en el VPS. Sigue docker compose logs -f caddy — esta vez debería obtener certificados reales para los dos dominios.
  6. Apaga el túnel de la Mac una vez que confirmes que el VPS funciona: 
    sudo launchctl unload /Library/LaunchDaemons/com.cloudflare.<tunnel-id>.plist
# o: cloudflared service uninstall
    Detén también el docker compose local en la Mac (o déjalo como respaldo frío — tú decides).

Desde aquí, todo lo de docs/deploy-vps.md aplica sin cambios (backups, R2, operación día a día, el split de backends).

Solución de problemas

  • La zona de Cloudflare queda "Pending": los nameservers no propagaron todavía desde GoDaddy. dig +short NS wabos.co debería mostrar los de Cloudflare — si después de varias horas sigue mostrando los de GoDaddy, revisa que hayas guardado el cambio de nameservers en el panel de GoDaddy (no solo los registros DNS).
  • cloudflared tunnel route dns falla con "zone not found": la zona todavía no está Active en Cloudflare — termina el Paso 0 primero.
  • La landing o la app muestran la página de error por defecto de Cloudflare, no WABOS: revisa docker compose ps (¿Caddy está arriba?) y que el ingress de wabos-config.yml tenga los dos hosts apuntando a http://localhost:80.
  • Avisos de certificado en el VPS después de cambiar del túnel: confirma que los registros DNS en Cloudflare estén en DNS only (nube gris), no proxied — un registro proxied (nube naranja) rompe el desafío ACME de Caddy.
  • Los botones de la landing apuntan a localhost:3000: no se puso NEXT_PUBLIC_APP_URL antes del build — ponlo y reconstruye con --build (queda compilado en el JS, sea túnel o VPS).
  • Todo lo demás (WhatsApp no conecta, la subida de imagen dice "no configurado", resetear la base de datos): ver la sección de Solución de problemas de la guía de despliegue.
