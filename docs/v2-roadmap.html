Deliberate divergences from the original plan

  • Auth: built-in JWT, not Clerk — no external dependency or per-MAU cost; drops straight into the existing bearer/localStorage model. (Clerk remains an easy later swap.)
  • Dev Postgres: embedded-postgres (a real PG binary in node_modules, no Docker/system install) instead of Neon-for-dev. Production still points DATABASE_URL at managed PG (Neon/Supabase/RDS).
  • Model tiering is tag-driven (Haiku→Sonnet on buying-intent tag) rather than per-employee roles.
  • FAQs kept separate from the new knowledge base (different shape; avoided migrating live data).

Still deferred (post-v2)

  • Stripe billing + AI-message metering/overage (caps exist; hard-metering needs billing design).
  • Multi-workspace switcher UI — the model supports one account owning many businesses (via X-Business-Id); the dashboard picker isn't built yet.
  • Worker-per-tenant fleet + DB-backed Baileys creds — needed only at large scale; the single-process connection manager covers the first tens of tenants.
  • Apple sign-in — needs a paid Apple Developer account + an HTTPS domain (can't run on localhost).
  • Official WhatsApp Cloud API adapter (§5).

Where V1 stands

V1 is a real, working end-to-end system: QR connect, realtime inbox, Claude-powered AI Employee with tools, CRM, catalog, and throttled broadcasts — single-tenant, SQLite, one engine per WhatsApp number. It's enough to onboard real clients (the STAND 120 demo proves the flow). But it was built to be correct, not yet to be operated at scale. v2 closes that gap.

0. Pay down V1 debt first ✅ shipped

All four shipped (see build status). Original rationale kept for reference:

  • Prompt caching in ai/employee.ts: mark the system block (profile + FAQs + catalog) with cache_control. Cache reads bill at ~0.1× input — the single biggest cost lever. (See Dev §6.)
  • Per-employee model tiering: Sales → claude-sonnet-5, everyone else → claude-haiku-4-5. Roughly halves blended cost.
  • A minimal test suite around the message pipeline and API before refactors begin.
  • Durable broadcast queue so an engine restart resumes instead of stranding recipients as pending.

1. Multi-tenancy — the headline of v2 ✅ shipped

V1 is one engine per business. To run hundreds of clients you need one system serving many tenants. This is the biggest architectural change and everything else depends on it. Built as Phases A–D (see build status) — with two deliberate changes from the plan below: auth is built-in JWT (not Clerk), and dev Postgres is embedded-postgres (managed PG in prod).

The plan (as executed)

  1. Add business_id (nullable → then required) to every table. The V1 schema was designed for exactly this — no rewrite, just a migration and a scoping layer.
  2. Move from SQLite to Postgres (Neon on the Vercel Marketplace, or managed PG). SQLite is great per-tenant but caps concurrency for a shared multi-tenant DB.
  3. Auth & orgs: replace the single DASHBOARD_TOKEN with real users, orgs, and roles (Clerk via the Vercel Marketplace is the fast path). Row-level scoping by business_id on every query.
  4. Plan gating: enforce the plan limits in code — AI-message caps with overage, user/number/contact limits, feature flags per plan.
  5. The WhatsApp connection problem: each tenant still needs its own long-lived Baileys socket. Two viable shapes:
    • Connection manager: one engine process holds many sockets (a map of business_id → WASocket), sharing the DB and API. Simpler ops, but one crash affects many tenants.
    • Worker-per-tenant: an orchestrator spawns/monitors an isolated worker per number (Docker/systemd/pm2 fleet). Better isolation and ban-blast-radius control; more moving parts.
    Recommendation: start with the connection manager (batched, e.g. 50–100 numbers per process), evolve to workers for Pro/Empresarial where isolation matters.
Ban isolation is a multi-tenancy requirement, not just an ops nicety. One tenant's banned number must never take down another's. Keep each tenant's auth/ and send-queue fully separated regardless of which shape you pick.

2. Payments — Yape / Plin / cards v2 core

Peru-first. Two layers:

  • Collections for the client's customers: the AI verifies Yape/Plin receipts (image → confirmation), sends payment reminders, tracks overdue. Ties into the existing Collections employee.
  • Billing for us (the operator): recurring card via Culqi/Izipay, plus Yape/Plin for smaller plans. Automate the subscription lifecycle described in Owner §8.

Add-on integrations to sequence: Culqi, Izipay, Mercado Pago; later Stripe for cross-border.

3. Inventory · analytics · mobile v2

  • Inventory sync — stock counts feeding the catalog; the AI stops offering out-of-stock items automatically.
  • Analytics dashboards — sales, response times, conversion rates, popular products, retention, revenue (the WABOS Analytics module from the vision). Instrument events now so the data exists later.
  • Mobile app — the inbox is where owners live; a native/PWA app for replies + notifications drives daily engagement and cuts churn.
  • Media handling — download and store images/audio (V1 only labels them). Needed for receipt verification and richer catalog.

4. Build-it-right foundations (apply throughout)

PracticeWhy it matters for WABOS
Migrations (Drizzle/Prisma or SQL migration files)Once multi-tenant, schema changes touch live client data — no more idempotent CREATE IF NOT EXISTS.
Automated tests (pipeline, API, AI tool loop)The message pipeline is the product; regressions there lose messages. Add before big refactors.
Durable queue (BullMQ / Vercel Queues) for sends & broadcastsSurvives restarts, enables retries and rate-limit backpressure across tenants.
Observability (structured logs, per-tenant metrics, alerts)You can't run a fleet you can't see. Connection uptime, AI cost/tenant, ban signals — see Owner §7.
Feature flags & staged rolloutShip risky changes (new model, new pipeline) to a few tenants first.
CI (typecheck + tests on every PR)Keeps the monorepo honest as contributors grow.
Config over code for AIPer-tenant model choice, tone, and prompt cached separately — don't hardcode.
Keep the WhatsApp boundary sacred. Baileys stays confined to the wa/ layer (V1 already does this). Every foundation above should preserve that seam so the official-API adapter in §5 drops in cleanly.

5. Official WhatsApp API adapter strategic

Baileys (unofficial) is right for SMB acquisition — free, instant QR onboarding. But for large clients where a ban is existential, offer the WhatsApp Business Platform (Cloud API) as a premium option. Because V1 isolates the WhatsApp layer in apps/engine/src/wa/, this is an adapter, not a rewrite: implement the same inbound/outbound interface against the Cloud API webhooks + send endpoints, and let the plan decide which transport a tenant uses. This becomes an Empresarial upsell and a real answer to the ban objection.

7. Beyond v2 — the v3/v4 vision

  • v3 — Voice: AI voice receptionist (speech-to-speech), WhatsApp calling integration when available. The voice-note AI add-on is the on-ramp.
  • v4 — Marketplace & platform: installable apps (Delivery, SUNAT/facturación electrónica, Shopify, WooCommerce, Mercado Libre, Google Calendar), developer APIs, webhooks, and full white label. This is where WABOS stops being an app and becomes the operating system for businesses that run on WhatsApp.
