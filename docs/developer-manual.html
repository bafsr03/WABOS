1. Architecture

WABOS is two apps because Baileys holds a persistent WebSocket to WhatsApp — it needs a long-running process and cannot run on serverless (Vercel, Lambda, etc.).

Customer ─▶ WhatsApp ─▶  Engine (Node, always-on)            Dashboard (Next.js)
                        ├─ Baileys WebSocket      ◀─REST+WS──┤  Inbox · CRM · Catalog
                        ├─ SQLite (better-sqlite3)           │  Broadcasts · Settings
                        ├─ Fastify API + /ws                 └  Connect (QR)
                        └─ AI Employee (Claude + tools)
  • Engine (apps/engine) — owns the WhatsApp connection, the database, the API, and the AI. Runs locally now, on a VPS/pm2 in production.
  • Dashboard (apps/dashboard) — Next.js app; talks to the engine over REST + WebSocket with a bearer token. Can deploy anywhere (incl. Vercel) as long as it can reach the engine.
Do not try to move the engine to serverless. The whole point of the split is that the engine is stateful and long-lived. Serverless would drop the WhatsApp socket on every cold start.

3. Data model (SQLite, WAL)

Defined in apps/engine/src/db/index.ts. Foreign keys on, WAL journal mode. Schema is created idempotently on boot (CREATE TABLE IF NOT EXISTS).

TablePurpose / key columns
settingskey/value: business profile, ai_enabled, tone, instructions
contactsjid (unique), phone, name, notes
tags, contact_tagsCRM tags (many-to-many)
conversationsone per contact; mode (ai|human), unread_count, last_message_at
messageswa_message_id (unique, dedupe), direction, type, text, from_ai, timestamp
productsname, description, price, currency, active
faqsquestion, answer — fed into the AI system prompt
broadcasts, broadcast_recipientscampaign + per-contact status/counters
Multi-tenant-ready: the schema is single-tenant but designed so a nullable business_id can be added to every table later without a rewrite. See v2 Roadmap for the migration path.

4. The message pipeline (the heart)

Inbound flow, in wa/inbound.ts:

  1. messages.upsert fires → ignore groups / status / newsletters / channels; both incoming and own (fromMe) messages are persisted, but only incoming ones trigger the AI.
  2. Upsert contact + conversation (modules/store.ts), persist the message. wa_message_id has a unique index → duplicates are silently dropped.
  3. Every persisted message emits message.new + conversation.updated on the event bus → forwarded to the dashboard over WS.
  4. If conversation mode = 'ai' and global ai_enabled = '1': a 4 s debounce batches rapid messages, then re-checks mode (owner may have taken over) and calls runAiEmployee().
  5. The reply goes out through the outbound queue (wa/outbound.ts): sendPresenceUpdate('composing'), 2–5 s humanized jitter, send, persist as outbound from_ai.

Any manual reply from the dashboard flips the conversation to human (in the API route); a "Resume AI" toggle flips it back. Global kill-switch: the ai_enabled setting.

5. WhatsApp layer (Baileys)

wa/connection.ts is the only place that imports Baileys. This is a deliberate boundary — a future WhatsApp Cloud API adapter can replace it without touching the rest.

  • useMultiFileAuthState(config.authDir) persists credentials to auth/. Restart ⇒ no re-scan.
  • Connection state machine: connecting → qr → connected, with exponential backoff reconnect on close. On DisconnectReason.loggedOut it wipes auth/ and re-issues a QR.
  • QR is printed to the terminal (qrcode-terminal) and emitted as wa.status for the dashboard, which renders it as a data-URL (qrcode).
  • getSock() throws unless connected — outbound code must handle that.
Anti-ban guardrails live here and in outbound.ts/broadcasts.ts: serialized global send queue, 2–5 s typing jitter on AI replies, 6–12 s randomized spacing on broadcasts, groups/status ignored. Never remove or "speed up" these.

6. AI layer (Claude)

ai/employee.ts builds the system prompt from settings + faqs + products, collapses message history into alternating turns, and runs a tool loop (max 5 iterations) with @anthropic-ai/sdk.

Tools (ai/tools.ts):

ToolEffect
search_catalog(query)LIKE query over active products
handoff_to_human(reason)flips conversation to human, notifies dashboard
tag_customer(tag)adds a CRM tag (buying intent)
Cost-critical improvements not yet wired (do these before scaling):
  • Prompt caching: the system prompt (profile + FAQs + catalog) is rebuilt every call and not cached. Add cache_control: {type:'ephemeral'} to the system block — the prefix is stable per business, so cache reads bill at ~0.1×. This is the single biggest margin lever.
  • Model tiering: V1 uses one AI_MODEL (default claude-sonnet-5) for everything. Run the Support/Receptionist/Collections employees on claude-haiku-4-5 and reserve claude-sonnet-5 for Sales. See Pricing §4.
Current pricing (per MTok): Sonnet 5 $3/$15, Haiku 4.5 $1/$5; cache reads ~0.1× input.

Model IDs are current as of this build: claude-sonnet-5, claude-haiku-4-5, claude-opus-4-8. Do not append date suffixes to these aliases. Thinking is adaptive-only on the 5-series — never pass budget_tokens.

8. Realtime (WebSocket)

events.ts is a single in-process EventEmitter. The API's /ws route (token via query string) subscribes each client and forwards every WabosEvent. Event types: wa.status, message.new, conversation.updated, broadcast.progress. The dashboard's lib/ws.ts auto-reconnects.

9. Local development

pnpm install
cp apps/engine/.env.example apps/engine/.env   # set DASHBOARD_TOKEN + ANTHROPIC_API_KEY
pnpm seed            # demo data (STAND 120)
pnpm dev             # engine :4000 + dashboard :3000 (parallel)
# or: pnpm dev:engine / pnpm dev:dashboard in separate terminals
pnpm typecheck       # tsc --noEmit on both apps

The engine hot-reloads via tsx watch. If you delete data/wabos.db while the engine runs, stop it first — an open handle keeps a stale view.

10. Adding a module (the pattern)

Every module follows: data access in modules/ → routes in api/server.ts → emit bus events → dashboard page under app/.

  1. Add tables to the schema in db/index.ts (idempotent).
  2. Write typed data-access functions in a new modules/<thing>.ts (mirror store.ts — prepared statements, return typed rows).
  3. Register Fastify routes in api/server.ts with zod validation.
  4. Emit bus.emitEvent(...) for anything the dashboard shows live.
  5. Add a Next.js page using lib/api.ts + connectWs, wrapped in <Shell>.

11. Known gaps / tech debt (V1)

  • No prompt caching or model tiering yet (see §6) — do before scaling clients.
  • Single-tenant: one engine per WhatsApp number. Multi-tenancy is the v2 headline.
  • SQLite is fine per-tenant but caps concurrency — Postgres in v2 for multi-tenant.
  • Broadcasts run in-process; an engine restart mid-campaign leaves recipients pending (no resume). A durable queue (BullMQ / Vercel Queues) is a v2 item.
  • Media (images/audio) is stored as a placeholder label, not downloaded. Media handling is v2.
  • Smoke-tested via curl; no automated test suite yet.

12. Conventions

  • TypeScript strict, ESM ("type":"module", NodeNext resolution) in the engine.
  • Validate all request bodies with zod; never trust client input.
  • Keep the Baileys import confined to wa/connection.ts.
  • All outbound WhatsApp traffic goes through the queue in outbound.ts / broadcasts.ts — never call sock.sendMessage directly from a route.
  • Secrets (ANTHROPIC_API_KEY, DASHBOARD_TOKEN) only in .env; auth/ and data/ are gitignored.
