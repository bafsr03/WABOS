🔄 Cómo actualizar WABOS en vivo

La forma correcta de probar algo nuevo sin romper lo que ya funciona: desarrolla en tu Mac, pruébalo ahí con calma, y solo cuando estés seguro lo subes al servidor (VPS) donde corre wabos.co. Nunca edites archivos directamente en el servidor — ese fue el problema que tuvimos al desplegar la primera vez.

Panorama: dos lugares donde vive WABOS

Hay dos copias del código funcionando al mismo tiempo, y es importante no confundirlas:

💻 Tu MacDonde escribes y pruebas código nuevo. Nadie más lo ve. Puedes romperlo y arreglarlo sin problema.
→
🐙 GitHubEl repositorio — la versión "oficial" del código. Es el punto intermedio entre tu Mac y el servidor.
→
🌐 VPS (OVH)El servidor real, corriendo 24/7, sirviendo wabos.co y app.wabos.co a tus clientes de verdad.
Regla de oro: el código siempre viaja en una sola dirección: Mac → GitHub → VPS. Nunca al revés, y nunca edites algo directo en el VPS que no exista también en tu Mac — si lo haces, la próxima actualización lo puede borrar sin que te des cuenta.

1 · Desarrollar y probar en tu Mac

Todo cambio empieza aquí, nunca en el servidor.

1 Abre una terminal en la carpeta del proyecto: 
cd ~/Desktop/WABOS
2 Prende los tres servicios a la vez (motor + dashboard + sitio web), cada uno con recarga automática al guardar un archivo: 
pnpm dev
Esto abre:
  • localhost:3000 — el dashboard (la app que usan tus clientes)
  • localhost:3001 — el sitio web / marketing (wabos.co)
  • el motor (API + WhatsApp) corriendo en segundo plano

Si solo quieres prender uno: pnpm dev:dashboard, pnpm dev:web o pnpm dev:engine.

3 Haz tu cambio: edita el archivo, guarda, y revisa en el navegador (localhost:3000 o 3001) que se vea/funcione como esperabas. Con pnpm dev no hace falta reiniciar nada — recarga solo.
Esto corre completamente separado de wabos.co. Puedes experimentar, romper cosas y probar ideas a medio terminar sin ningún riesgo para tus clientes reales.

2 · Antes de subir nada, pruébalo bien

Una vez que el cambio se ve bien en localhost, antes de mandarlo al servidor conviene revisar dos cosas rápidas:

  • ¿Compila sin errores? Corre pnpm build en la raíz del proyecto — esto es exactamente lo que el servidor va a intentar hacer. Si falla acá, fallará en el VPS también, así que es mejor descubrirlo ahora.
  • ¿Probaste el flujo completo? No solo el botón que cambiaste — usa la app un poco alrededor de tu cambio para asegurarte que no rompiste algo cercano (por ejemplo, si tocaste el login, prueba registrar, iniciar sesión y cerrar sesión).

3 · Guardar el cambio (commit y push)

Cuando estés conforme con el cambio, lo guardas en git y lo subes a GitHub:

git add -A
git commit -m "descripción corta de qué cambiaste"
git push origin main
Si trabajas en una rama separada (por ejemplo feat/algo-nuevo) en vez de main, primero haz el push a esa rama, revisa que todo esté bien, y luego mézclala a main con git checkout main && git merge feat/algo-nuevo && git push origin main. El VPS siempre actualiza desde main.

4 · Llevarlo al VPS (el paso que lo pone en vivo)

Con el cambio ya en GitHub, ahora sí entras al servidor a traerlo y reconstruir la app.

1 Conéctate al servidor: 
ssh ubuntu@149.56.102.114
2 Entra a la carpeta del proyecto y trae el código nuevo: 
cd ~/wabos
git pull origin main
3 Reconstruye la imagen y reinicia todo: 
docker build --no-cache \
  --build-arg NEXT_PUBLIC_APP_URL=https://app.wabos.co \
  --build-arg NEXT_PUBLIC_GOOGLE_CLIENT_ID=$(grep -m1 '^NEXT_PUBLIC_GOOGLE_CLIENT_ID=' .env | cut -d= -f2-) \
  -t wabos:latest . && docker compose up -d --force-recreate

Tarda 1–3 minutos. Usamos docker build directo (no docker compose build) porque en este servidor el "cache" de Docker a veces no detecta bien los cambios y sirve una versión vieja — --no-cache fuerza a reconstruir todo desde cero, garantizando que el cambio realmente quede adentro.

¿Solo cambiaste algo que no afecta el sitio web/dashboard (por ejemplo lógica del motor de WhatsApp)? Puedes usar docker compose restart engine en vez de reconstruir todo — es más rápido. Pero si tocaste cualquier archivo dentro de apps/dashboard o apps/web, sí necesitas el docker build completo, porque esos son sitios compilados de antemano (no se actualizan solo con un restart).

5 · Verificar que quedó bien

  • Abre https://app.wabos.co y https://wabos.co en el navegador (con Cmd+Shift+R para forzar que no use una versión guardada en caché).
  • Revisa que los contenedores estén sanos: docker compose ps — todos deben decir Up / running, sin reinicios en bucle.
  • Si algo no carga, revisa los registros del servicio correspondiente: docker compose logs engine --tail 50 (o dashboard / web / caddy).

Si algo sale mal después de actualizar

No entres en pánico — el paso anterior que sí funcionaba sigue guardado en git. Puedes volver atrás:

1 En el servidor, mira el historial reciente y encuentra el commit anterior (el que sí funcionaba): 
git log --oneline -5
2 Vuelve a ese punto: 
git checkout <hash-del-commit-anterior>
3 Reconstruye igual que en el paso 4 de arriba. Esto te devuelve exactamente a la última versión que funcionaba mientras arreglas el problema con calma en tu Mac.
Después de arreglarlo en local, vuelve a hacer git checkout main en el servidor antes del siguiente git pull, para no quedarte "congelado" en un commit viejo.
